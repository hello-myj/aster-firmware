# 公共核心

这里存放 IDF、Zephyr 和主机测试共同使用的算法与格式实现。代码只依赖标准 C 和 `contract/include`；不包含操作系统、厂商驱动头文件或 `CONFIG_*` 条件分支。

- `package/`：ASTP 包、清单与 JSON 字段解析、ABI/目标/能力校验、溢出安全的区段边界检查。
- `net/`：HTTP 增量解码及 URL/头部处理、MQTT 帧编解码、WebSocket 握手与帧编解码。
- `include/`：不对齐输入安全的字节序读取工具。
- `sources.cmake`：两种构建系统读取的同一份源码及头文件目录清单。

包解析通过 `aster_pkg_policy_t` 接收目标架构、ABI、分配/释放、能力查询以及可选日志回调。系统适配器负责提供这些参数；公共层不判断自己运行在哪个系统。迁移保留了原有分配器与能力校验策略，不改变 APP ABI、包格式及持久化目录。

Zephyr 在 `systems/zephyr/CMakeLists.txt` 中引入公共头目录，并按服务开关选择源码。IDF 的 runtime/transport/render 组件读取同一清单。公共层不得反向引用 `systems/`；测试 `tests/test_common_package.py` 同时检查依赖边界，并在没有任何后端头文件的情况下编译真实解析器。

这是分阶段提取的第一步。以下实现仍在现有目录，两套系统尚未完全分离：

1. 安装事务、版本切换、应用注册与 KV：先定义文件读写、目录操作和锁的内部端口，再提取公共事务逻辑。
2. 网络服务状态机：保留这里已独立的编解码器，继续分离 socket、TLS、时钟与任务唤醒。
3. Launcher、字体和渲染：分离场景/排版逻辑与帧缓冲提交、PPA、并行执行及系统设置。

后续模块沿用同一规则：公共逻辑只有一份；系统目录实现端口；板级目录负责接线和硬件能力。每次迁移都需通过主机回归及两套真实目标构建。
