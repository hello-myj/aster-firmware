## 1. 目标与当前基线

让 APP 只使用 Aster SDK 即可访问远程 HTTP/HTTPS 服务、下载文件、进行 TCP/UDP 通信，不需要包含 Zephyr 或 ESP-IDF 头文件，也不需要安装固件开发环境。

当前源码基线：

- 工作区公共ABI为3.10.0（含有界TCP/UDP、HTTP/HTTPS和MP3分段输入，尚未发布）；此前发布的3.7成品不含新导入。
- SDK 已公开 Wi-Fi station 扫描、连接、断开、重连、状态和已保存 SSID 接口；需要 `wifi` 权限。
- 固件设置页有个人热点与 DHCP 服务，但 SDK 没有公开个人热点控制接口。
- 两款板的 `base.conf` 开启 socket、DNS、SNTP 和 TCP，关闭 IPv6；`CONFIG_ASTER_NET` 控制独立 TCP/UDP 服务与诊断 CLI。
- 两款板当前 `CONFIG_NET_MAX_CONTEXTS=8`、`CONFIG_NET_MAX_CONN=8`、`CONFIG_DNS_NUM_CONCUR_QUERIES=3`。服务最多两槽，CLI 同样占槽；其余为 DNS/SNTP/DHCP 等预留，仍需并发峰值验收。
- SDK已公开TCP/UDP七个aster_network_*导入，DNS作为连接/发送阶段；HTTP/HTTPS六个导入已提供，WebSocket、MQTT未提供。
- 两款板本轮将内核堆由48 KiB提升到96 KiB；微雪仍使用40 MHz、双8 KiB显示预拷贝。不将已有图形峰值和新增网络峰值混算，内核/libc分池与验收见第16节。

第一批完整网络版本包括 TCP/UDP、HTTP/HTTPS 和 MQTT/MQTTS 客户端，分阶段实施，按第15节硬件预算收敛：以两个活动APP传输连接作为验收目标、一个连接作为明确可选的低资源配置；先验收一个TLS会话，不承诺双TLS。MQTT 从后续候选提升为独立必做阶段；HTTP 服务端、TCP 监听、WebSocket 和其他服务仍按需扩展。

## 2. 总体约束

1. 网络等待不进入 UI/APP 执行线程，不让系统 workqueue 同步等待网络服务完成。
2. 网络缓存、任务、句柄和连接数均有硬上限；不能随响应体或远端数据无限增长。
3. APP 退出后，不再向其投递数据，不访问其 WASM 内存，资源能够回收。
4. 复用固件网络栈，不在每个 APP 中打包一份 TCP、HTTP 或 TLS 实现。
5. 固件拥有 socket 和证书；APP 只看到 Aster 句柄及稳定错误码。
6. HTTP/HTTPS 共用请求模型，HTTPS 默认校验证书和域名，不通过忽略校验完成验收。
7. SDK、模拟器、契约和开发手册同步更新，不能只在固件中增加 native import。
8. 新功能以能力查询和权限校验暴露；已有 APP 不增加网络依赖，也不被强制重新编译。

## 3. 分层与线程模型

数据路径：

```text
APP / WASM
  -> SDK net.h / http.h / mqtt.h
  -> WAMR native import：权限、边界、句柄、配额检查
  -> 固件网络服务：任务、状态、缓存、取消和生命周期
  -> 平台适配：Zephyr socket / DNS / HTTP Client / TLS
  -> Wi-Fi station 或个人热点网络接口
```

### 3.1 APP 侧

连接和请求接口提交任务后立即返回句柄；APP 在帧回调或定时器中查询状态、进行有界收发。首版不增加必须依赖的新事件类型，先使用现有 Wi-Fi 接口类似的“提交＋查询”模式。

禁止用以下方式实现异步外观：APP 线程调用一个内部仍会执行 DNS、阻塞 connect 或 TLS 握手的接口。接口返回时间必须通过不可达地址、慢 DNS 和慢服务器验证。

### 3.2 固件侧

- TCP/UDP 使用非阻塞 socket 和有超时的 poll，集中处理多个连接。
- HTTP Client 可能在一个请求内持续工作，应放在独立、有界的请求执行上下文，不能阻塞 TCP/UDP 调度。
- 网络执行上下文只读写服务私有缓存，不调用 LVGL，不执行 APP 回调，不把 WASM 指针交给后台线程。
- 取消信号必须能唤醒等待。DNS 如不能即时取消，先将结果作废，保留任务所有权直到解析真正结束；不能提前释放其上下文。
- 不默认创建“每 socket 一个永久线程”。先测量栈峰值，再决定固定线程数和栈大小。

### 3.3 生命周期与所有权

每个任务持有 APP 会话标识、句柄代数和取消状态。APP 重启即产生新会话；旧会话的延迟结果不能写入新会话，即使 APP ID 相同。

APP 退出时按顺序执行：停止接受该会话的新请求、使公开句柄失效、取消任务并唤醒等待、清理后台所有权，最后释放服务私有缓存。后台尚未结束时，任务对象不能释放或复用，也不能保留指向已销毁 APP 对象的指针。

`close` 可以先使 APP 句柄失效，但内部连接槽只能在底层工作确实结束后复用。关闭中的任务仍计入配额，防止通过连续打开/关闭绕过上限。

若底层驱动存在无法中断的等待，应明确列为阻塞项，修复后再验收；不能单靠上层计时器声称已经完成取消。

## 4. 权限、能力与 ABI

### 4.1 权限划分

- 拟新增 `net`：允许 APP 发起网络通信。
- 现有 `wifi`：允许扫描及改变 Wi-Fi station 连接状态。
- APP 通过已连接网络访问服务器，只需要 `net`；不自动获得 `wifi` 控制权限。
- 下载到文件仍需已有 `fs` 权限，并遵守 APP 沙箱路径；使用网络权限不能访问任意 SD 路径。
- 后续监听服务的权限和绑定范围在 N4 单独确定，不在首版中默认开放。

拟议 APP 声明：

```toml
# ABI3.9工作区HTTP/TLS能力已接入，N2尚在验收。
permissions = ["net", "fs"]
requires = ["network", "http", "tls"]
```

N1已锁定network能力位15及net权限位5；后续协议的额外能力和权限仍须随对应契约明确。能力表示本固件支持该功能，不表示已经获得 IP 或一定能访问互联网。安装与运行时的能力处理遵循项目现有规则，不能擅自改为所有缺少能力的包均无法安装。

### 4.2 ABI 扩展规则

- 新结构保留 `size`、`version`，使用固定宽度整数、显式长度和保留字段；不跨 ABI 传递宿主指针、`size_t`、`errno` 或原生 fd。
- 不改变现有错误码、事件值、能力位和导入签名；工作区采用ABI3.9，保留3.8TCP/UDP及更早接口，已与3.7冻结基线检查，无旧布局/签名/枚举破坏。
- 公共头文件以固件 `contract/include/aster` 为源，通过现有契约导出/导入流程同步 SDK，不手工维护两套接口。
- 新错误需按兼容流程追加，不能重排旧枚举。初期可用已有稳定错误码加结构化阶段/原因，不能直接泄露平台 errno 作为返回值。
- 新增能力需同步固件探测、包校验、SDK manifest、模拟器能力与文档。

## 5. 拟议公共接口

以下保留接口职责草案，不能按草案函数名调用。TCP/UDP本轮已统一为aster_network_get_info/open/send/recv/status/cancel/close，准确签名和规则以contract/include/aster/network.h及SDK开发手册第15节为准。get_info返回只读接口/IPv4快照与限额，status返回指定连接状态，二者独立。

### 5.1 网络状态

已实现的`aster_network_get_info(...)`返回只读接口标志、本机IPv4提示和连接/队列限额，结构44字节；锁忙EAGAIN，没有接口时OK且flags=0。它读取OS缓存，不触发扫描、联网或外部探测。UP只表示启用；ESP载波可能在未关联时保留，不把原始CARRIER标志当作Wi-Fi关联证明。

区分以下情况：没有接口、接口未连接、等待地址、具备本地 IP。具备 IP 不等于互联网可达；个人热点本地通信也不等于具备 NAT 或上网能力。

连接接口直接接受域名或 IPv4 地址。首版可不单独公开 DNS 查询，解析作为连接任务中的一个阶段，必须有限时和错误原因。

### 5.2 TCP

- `aster_tcp_connect(...)`：复制主机名/地址、端口、超时参数，提交异步连接，返回句柄或负错误。
- `aster_tcp_status(...)`：查询解析、连接中、已连接、对端半关闭、失败、取消等状态，以及阶段、结果和计数。
- `aster_tcp_send(...)`：将数据复制到有界发送队列，返回实际接受的字节数；无空间时返回 `ASTER_EAGAIN`。
- `aster_tcp_recv(...)`：复制已收到的数据，返回实际长度；暂时无数据返回 `ASTER_EAGAIN`。
- `aster_tcp_close(...)`：请求关闭、使句柄失效，重复关闭返回稳定的无效句柄错误。

TCP 语义必须明确：

- 一次 send 对应的内容可能被多次 recv 读出，多次 send 也可能合并接收；不保证消息边界。
- send 成功只表示进入本地队列，不表示远端应用已经处理；状态中区分排队与实际发送统计。
- `recv` 的容量必须大于 0；已有缓存先读完，对端有序 EOF 且缓存空时才返回 0。
- 连接异常、超时和正常 EOF 分开表达；是否允许异常后先读完缓存必须固定，并在两端实现一致。
- Zephyr 4.4.2 原生 TCP 不支持半关闭后继续写；首版所有运行环境在读到 EOF 后拒绝新发送，已缓存接收数据仍先读完，未发完队列遇到 EOF 报失败。真正半关闭写能力另行扩展，不用模拟器的 POSIX 行为冒充设备已支持。
- 首版不自动重新连接，避免静默重复提交业务数据。需要重连的 APP 自己决定协议恢复和重试。

### 5.3 UDP

- `aster_udp_open(...)`：创建有界数据报端点，返回句柄。
- `aster_udp_sendto(...)`：发送一个数据报，返回完整长度或错误，不提供模糊的“半个数据报已接受”语义。
- `aster_udp_recvfrom(...)`：返回一个完整数据报及来源地址、端口；暂时没有数据返回 `ASTER_EAGAIN`。
- `aster_udp_close(...)`：释放端点。

接收缓冲不足时返回所需长度并保留该包供重试；不得静默截断。队列满时可丢包，但必须有丢包计数。UDP 允许零长度数据报，因此不能把返回 0 当作 TCP EOF。

首版仅单播 IPv4。广播、多播、设备发现和端口绑定策略需另行规定；数据报端点不等于已经开放 TCP 监听服务。

### 5.4 HTTP/HTTPS

- `aster_http_request(...)`：复制请求配置，校验 URL、方法、请求头和上传体上限，返回请求句柄。
- `aster_http_status(...)`：查询解析/连接/握手/响应头/响应体/完成/失败/取消，HTTP 状态码、结果和字节数。
- `aster_http_header(...)`：按名称、序号获取响应头；保留同名多值，不简单用逗号拼接所有头。
- `aster_http_read(...)`：分块读取响应体，无数据但尚未结束返回 `ASTER_EAGAIN`。
- `aster_http_cancel(...)`：取消请求，保留句柄以便查询最终状态。
- `aster_http_close(...)`：取消未完成操作并使句柄失效；内部资源按真实完成时机回收。

首版行为：

- 支持 GET、HEAD、POST，以及带显式长度的小型二进制请求体；JSON 视为普通 UTF-8 字节，不在网络层自动解析。
- 支持 Content-Length、chunked 和连接关闭作为结束标志的响应；自动去除 HTTP 分块编码。
- HEAD、204、304 等无响应体语义必须正确，不等待不存在的数据。
- 404、500 等是有效 HTTP 响应，HTTP 状态与传输错误分别返回。
- 响应体分块交给 APP，不按 Content-Length 分配整块内存。默认请求 `Accept-Encoding: identity`；压缩响应首版不自动解压，文档说明 APP 看到的内容。
- 上传体首版在提交时复制，有硬上限；大文件流式上传后续增加，不用无限复制冒充流式上传。
- 头字段名、值和 URL 校验禁止 CR/LF 注入；响应头达到上限时明确失败。
- 重定向次数有上限；跨 origin 不转发 Authorization/Cookie 等敏感头，默认拒绝 HTTPS 降级为 HTTP。需要重放上传体或改变方法的重定向规则必须显式测试。
- 首版不做自动 Cookie 持久化、HTTP/2、透明请求重试、连接池或无限 keep-alive。
- 正常完成且缓存排空后 read 返回 0；失败/取消的读完缓存与终态报告顺序在契约中固定。

### 5.5 MQTT/MQTTS

MQTT 适合设备状态上报、传感器数据、远程命令和消息订阅。使用固件的客户端库连接外部 broker，不在设备上运行 broker，也不把业务主题设计写死在固件里。

首版采用 MQTT 3.1.1、TCP/TLS 传输、QoS 0/1。配置包括 broker 主机/端口、client ID、用户名/密码、keepalive、clean session、遗嘱主题/内容/QoS/retain，以及可选重连策略。协议版本、TLS 验证与资源上限不由 APP 任意绕过。

拟议接口：

- `aster_mqtt_connect(...)`：复制配置、提交异步连接，返回 APP 专属句柄。
- `aster_mqtt_status(...)`：查询连接、认证、重连状态、稳定错误原因、队列和丢弃计数。
- `aster_mqtt_subscribe(...)`、`aster_mqtt_unsubscribe(...)`：返回操作 ID；提交成功不等于 broker 已接受订阅，另行查询 SUBACK/UNSUBACK 结果。
- `aster_mqtt_publish(...)`：复制有界 topic/payload，返回消息操作 ID；队列满返回背压错误。
- `aster_mqtt_result(...)`：查询提交操作的完成结果；完成记录也有上限和明确回收规则。
- `aster_mqtt_recv(...)`：取出一条消息及 topic、QoS、retain、dup 等元数据；长度不足时不静默截断，返回所需容量。
- `aster_mqtt_disconnect(...)`：异步有序断开，结果可查询；不再自动重连。
- `aster_mqtt_close(...)`：取消任务并使句柄失效，内部资源结束后回收。

实现与语义要求：

1. MQTT payload 是二进制，可含 NUL，也可为空；topic 按协议校验 UTF-8，发布 topic 不允许订阅通配符。订阅过滤器支持协议规定的 `+`、`#` 并进行长度/语法检查。
2. QoS 0 本地发送完成、QoS 1 收到 PUBACK、远端业务实际执行是不同状态。QoS 1 可能重复，远程控制 APP 用业务命令 ID 去重，不宣称端到端 exactly-once。
3. 接收 QoS 1 首版采用服务完整接收并放入 APP 有界队列后确认；不在完整 payload 尚未保存时提前 ACK。该确认不等于 APP 已处理或写盘，APP 退出/设备掉电后不承诺消息仍保留。需要业务可靠性时另加业务 ACK。
4. 队列满时不阻塞整个网络调度；针对 QoS 0 丢包计数、QoS 1 暂停/断开且不提前确认的处理在实现前固定。超上限消息按协议消费或关闭连接，不能留下未读 payload 破坏下一包解析。等待空位不能无限阻止心跳。
5. 首版固定 clean session=true，对持久会话请求返回不支持；重连后的重订阅由固件依据有界主题表完成，记录每个 SUBACK 的真实结果。持久会话和跨重启离线队列后续设计，不在首版暗中启用。
6. 自动重连显式配置，使用有上限的指数退避和随机抖动；认证/证书拒绝不按瞬时网络抖动无限快速重试。不得自动重放结果不明的 QoS 0 业务消息；QoS 1 在途消息按协议会话语义管理，不能伪造 PUBACK。重连计数和最终失败原因可查询。
7. retain 是 broker 保存最后保留消息的机制，不是设备本地离线队列。遗嘱用于异常断连；正常 DISCONNECT 通常不触发遗嘱，示例明确这一区别。
8. 心跳由服务线程维持，APP 临时被下拉栏遮挡时仍工作；APP 退出默认关闭连接，不变成隐式后台常驻服务。正常退出尽力完成有序断开，并设定最大清理时间；异常断电交给 broker 按协议判定遗嘱。
9. 拟从每 APP 一个 MQTT 客户端、最多4个订阅、2条待收消息、2条待发消息和1条 QoS 1 在途消息起步；topic 初始上限128字节，payload 1024字节。以上队列分别计入统一网络预算，不能叠加后突破总额，最终数值以两板峰值为准。
10. 接收消息、操作结果与状态先采用有界轮询；若后续增加事件，只通知句柄/操作 ID，payload 仍通过读取接口领取。broker 密码和认证信息不写日志或示例源码。

## 6. 内存、配额与背压

N1已据两板实测固定：上下文8、连接处理项8、DNS并发3/服务器上限1，APP与CLI共用两槽；包描述符RX8/TX8、数据分片256字节RX24/TX32。缓冲数组增量12160字节位于PSRAM，内核堆保持96KiB。

以下涉及HTTP/TLS/MQTT的数值仍是调优起点，须在N2/N3根据实际峰值定版：

- 96 KiB配置以每APP最多2个活动传输连接为验收目标，先跑通单连接，再完成双连接回归；若双连接未通过，显式报告单连接配置，不能静默降低约定额度。HTTP/MQTT使用的底层连接计入同一总预算，不能额外绕过限额；控制操作/结果记录有单独有界槽位，不把一个订阅操作误算成一个socket。
- 同时最多 1 个 TLS 连接。系统服务与 APP 分配分别统计，保留系统所需容量。MQTTS 长连接也占这个名额；该初始配置不能承诺 MQTTS 与 HTTPS 同时运行，额度不足明确返回忙，不擅自断开 MQTT 或让 HTTPS 无限排队。若实际 APP 需要二者并存，先实测两个 TLS 会话的峰值，再调整交付配置。
- TCP 初始 RX/TX 队列各 2 KiB，单连接共4 KiB，优先评估服务私有PSRAM缓存；另加对象、栈、协议及TLS开销，不默认全部挤入内核堆；两连接仅此队列即共8 KiB，协议/线程另计。
- HTTP 响应体队列初始 2 KiB，允许分块读取更大的响应；HTTP对象与其内部TCP缓存避免重复中转，实际保留的每一份数据均计入预算。
- URL 初始上限1024字节，请求头与响应头分别最多2 KiB，提交时复制的上传体最多2 KiB；超过上限明确失败。这是精简默认配置，不能声称支持任意站点的大Cookie/响应头。统计包括终止符、描述符等附加空间，不只统计用户可见文本。
- UDP 数据报初始上限1200字节，接收队列最多2包；更大数据报和 IP 分片不作为首版承诺。
- APP 可指定下载总字节上限与总超时，超限明确失败；不能只信任远端 Content-Length。

接收队列满时 TCP/HTTP 暂停读取，通过传输层背压限制增长；UDP 按既定丢包策略处理。APP 慢读期间仍处理取消、关闭和其他连接，不持服务全局锁等待队列空间。

PSRAM 可用于适合的有界缓存，但不得假设网络驱动、TLS 分配和线程栈都能直接移到 PSRAM。内部 RAM、PSRAM、系统网络池与 APP 线性内存分别记账。加入网络功能后仍保持当前屏幕 DMA 所有权约束。

必须记录：静态 DRAM/IRAM/Flash 增量、网络线程栈峰值、动态堆与 PSRAM 起止/峰值、连接/任务峰值、TLS 握手峰值、系统服务并发开销、退出后的回收结果。

## 7. 超时、取消与错误

参数需分别覆盖 DNS、TCP connect、TLS 握手、发送/接收空闲和 HTTP 总时长，并有固件最大允许值。使用单调时钟计算截止时间；取消不能等待用户设定的长请求超时后才生效。

N1 先确定取消响应目标，再用慢 DNS、无响应 TCP、慢 TLS、满 RX/TX 队列测量。未测前不承诺“固定多少毫秒内全部释放”。状态结构建议包含：阶段、稳定结果码、协议状态、已接收/已发送/排队字节和可重试提示。

网络故障与本地参数/权限/句柄错误分开；APP 不能因错误丢失而无限轮询。日志不输出密码、Bearer Token、Cookie、私钥、完整认证请求头或默认打印响应体。

## 8. HTTPS 与证书

1. 在固件启用TLS及所需加密组件，按当前Zephyr版本配置编译。N2首版在N1 TCP服务之上接入Mbed TLS BIO，复用现有队列与两个连接名额，不额外建立TLS socket绕过预算；不要求APP安装Espressif驱动库。
2. 默认校验证书链、主机名和有效期，设置 SNI。握手阶段纳入超时和取消。
3. 检查设备墙钟有效性；时间未就绪应明确返回原因。单调计时的超时不受 NTP 校时跳变影响。
4. 明确 CA 来源、资源版本、安装位置和更新机制，支持本地测试 CA；首版不开放任意忽略校验选项。
5. 若允许 APP 自带 CA，必须限定证书数量/长度、APP 所有权、释放时机；不能自动成为所有 APP 的系统信任根。
6. 最低交付范围采用普通服务端认证；双向 TLS 和设备私钥管理后续单独设计。
7. 证书不匹配、过期、未知 CA、时间无效、握手取消均纳入自动化。真实互联网测试只作补充，可控本地 TLS 服务器作为主要验收基线。

### 10.0 所有协议统一采用“CLI先验收，再封装SDK”的顺序

本节适用于N1–N3及N5每个新增模块，不是等全部协议CLI写完以后才开始SDK。按单个模块逐项推进：

1. **先设计契约**：固定异步状态、句柄、错误、数据边界、超时、取消、权限和资源预算。此时可编写接口草案及模拟测试夹具，不把未实现导入加入正式SDK。
2. **实现固件公共网络服务**：底层网络及后台任务独立于shell、WAMR和UI；服务接收明确的内部owner/session，管理连接与缓存。
3. **增加设备shell CLI并验收**：CLI只是服务的调试客户端，提交后立即回到提示符，通过status/result/read查询结果，不在shell中另写一套阻塞DNS、TCP、HTTP或MQTT实现。
4. **CLI验收通过后接native/SDK**：添加权限、WASM地址与长度检查、APP专属句柄及退出清理，通过现有契约导出/导入流程同步头文件。不得直接把CLI命令字符串当SDK内部传输协议。
5. **SDK示例APP验收**：验证真实WASM/AOT调用、慢网络时绘制和触摸、上下拉恢复、取消/退出、旧会话回调隔离及资源回收。
6. **同步模拟器与文档**：同名接口及行为一致，完成Windows/Linux集成与两板记录后才视为该模块完整交付。

CLI和SDK调用的是同一个固件服务。两者可有不同的入口权限和显示格式，但连接状态机、TLS配置、配额、缓存、错误映射、取消与回收不能各维护一套。

#### CLI命令与后续草案

设备shell使用`aster net`命名空间；它不同于主机SDK的`aster`构建/部署命令。TCP/UDP、status、stats、result、cancel和close已实现，准确语法和边界见[网络CLI说明](network-transport-cli.zh-CN.md)。下面混列的HTTP/MQTT以及`result --operation`仍是后续草案，不可作为现有命令执行。

```text
aster net status
aster net stats
aster net tcp connect --host <host> --port <port> --timeout-ms <ms>
aster net tcp send <handle> --hex <data>
aster net tcp recv <handle> --max-bytes <limit>
aster net udp open
aster net udp sendto <handle> --host <host> --port <port> --hex <data>
aster net udp recvfrom <handle> --max-bytes <limit>
aster net http start --method GET --url <url> --timeout-ms <ms>
aster net http header <handle> --name <name> --index <n>
aster net http read <handle> --max-bytes <limit>
aster net mqtt connect --profile <test-profile>
aster net mqtt subscribe <handle> --topic <filter> --qos <0|1>
aster net mqtt publish <handle> --topic <topic> --qos <0|1> --hex <data>
aster net mqtt recv <handle> --max-bytes <limit>
aster net result <handle> [--operation <id>]
aster net cancel <handle>
aster net close <handle>
```

最终语法在N1锁定；通用命令也必须检查句柄类型。返回内容采用有界、带明确前缀的记录，包含handle/operation、状态、稳定结果、协议状态和长度；数据按有上限的hex/分块输出并带校验，便于主机自动核对。异步日志、命令回显和任务结果分开解析，避免SNTP等无关日志的`failed`触发误判。

CLI测试连接也受服务总连接/内存上限约束，不能拥有绕过配额的隐藏通道。MQTT/TLS认证用隔离测试profile或凭据引用；生产密码、Token、私钥不放进会被历史/日志捕获的命令参数。串口仍与现有文件传输共用，测试脚本单进程持有端口，传输过程中不并发发送CLI命令。

## 14. 其他网络服务与功能优先级

下面是可选能力清单，不是全部默认编译或一次性交付的承诺。新增服务必须给出实际 APP 用例、内存与后台生命周期预算，并进入 SDK/模拟器验收。

### 14.1 基础必需：随 N1–N4 建立

- **网络状态与变化通知**：区分 station/热点、链路、地址、DNS 和请求错误。先查询后事件，不能把 Wi-Fi 已关联当作服务器可达。
- **连接恢复策略**：Wi-Fi 连接恢复由已有系统连接管理负责；TCP/HTTP/MQTT 恢复按各自协议和业务语义处理，防止两层同时无限重试。
- **DNS 与时间服务整合**：复用已有解析/SNTP，不另起重复服务。后续可公开有界 DNS 查询和时间同步状态；时间设置属于系统权限，普通 APP 不随意修改全机时钟。
- **TLS 与认证凭据管理**：统一证书、SNI、校验结果及凭据隔离。Token/密码存放方案必须区分“APP 隔离保存”和“硬件加密保护”，未实现后者时不宣称安全存储。
- **网络诊断与统计**：分阶段错误、连接数、RX/TX/丢包、超时、重连和峰值占用；系统诊断可增加 DNS/TCP/TLS/HTTP 连通测试。Ping 可选，不作为唯一连通判断，也不直接给 APP 原始报文权限。

### 14.2 优先扩展：完成基础后价值较高

- **WebSocket/WSS 客户端**：实时消息、远程控制、双向状态同步。需处理 ping/pong、分片、消息上限、关闭握手和背压；不与 TCP 的字节流读取语义混淆。
- **SSE 客户端**：服务器单向事件推送，如通知或流式文本。可建立在 HTTP 流式响应上，解析 UTF-8、事件行、`id`/`retry` 并限制行长；断线续传只在服务端支持 Last-Event-ID 时成立，不等于 WebSocket。
- **mDNS/DNS-SD**：手机或电脑通过服务发现找到设备，减少手填 IP。提供有界服务注册/查询、唯一命名和冲突处理，明确依赖局域网多播；不能保证所有手机热点或路由器都转发多播。
- **本地 HTTP 服务端与 WebSocket 服务端**：个人热点下的手机控制页面、设置和小文件传输。默认明确绑定接口、会话认证、请求体与客户端数上限；不同于已经完成的 HTTP 客户端。
- **配网服务**：热点配网页面可复用现有个人热点与 Wi-Fi 连接服务。Captive Portal 的 DNS/重定向及各手机系统兼容要单独验收；不劫持 HTTPS，不宣称所有手机都自动弹窗。BLE 配网是另一条外设/协议路线，不能当作已有 Wi-Fi 网络 API 的附带能力。
- **下载管理**：进度、取消、临时文件、哈希校验；Range/ETag 条件下的断点续传。服务器不支持续传或内容已变时重启下载，不把不同版本数据拼在一起。

### 14.3 根据业务选择

- **CoAP/DTLS**：低开销设备资源访问、观察与块传输；只在需要对接对应设备或平台时加入，与 MQTT 的消息分发用途分开评估。
- **LwM2M**：设备注册、配置、遥测与平台管理；有真实管理平台需求后再做，不为普通天气/音乐 APP 默认引入。
- **网络文件上传与同步**：文件流式上传、失败重试、限速与同步冲突策略。FTP、WebDAV 等按对接需求选择，不为了“协议齐全”全部实现。
- **固件/APP 在线更新**：网络负责下载，安装必须调用现有校验/安装流程。固件 OTA 还需核对分区、bootloader、签名、回滚和断电恢复；不能把 HTTP 下载完成当成已实现 OTA。
- **局域网发现与组播**：UDP 广播/组播与专用发现协议；需要单独限定端口、报文和接收队列，优先评估是否已有 mDNS/DNS-SD 可满足需求。
- **IPv6、代理与复杂企业网络**：依目标部署环境增加，不改变首版 IPv4/普通接入网络的承诺。

### 14.4 暂缓作为通用 APP SDK 功能

- 设备端 MQTT broker、透明路由/NAT、VPN、通用 SSH 服务、任意原始 socket、通用代理服务。
- HTTP/2、HTTP/3/QUIC、无限后台常驻联网、没有配额的长连接或离线消息队列。

这些功能并非不能做，但会显著改变内存、功耗、权限和维护范围，需要独立需求与验收。尤其个人热点本地通信、互联网共享和设备路由是不同功能，不合并宣称。

### 14.5 推荐最终推进顺序

N1 TCP/UDP与资源模型 → N2 HTTP/HTTPS → N3 MQTT/MQTTS → N4两板/模拟器/SDK完整验收。之后优先考虑 WebSocket、mDNS/DNS-SD、本地配网/HTTP服务端和下载管理；SSE、CoAP、设备管理与 OTA 按 APP 用例排期。

MQTT 和新增网络服务都只提供通信机制，不替 APP 决定业务主题、消息格式、命令授权、幂等与远端执行确认。


## 15. 按现有硬件资源收敛的推荐配置（优先于候选功能目录）

第14节是可选目录，本节才是当前两款板建议实际采用的范围。以下引用G9已有结果，不代表当前新网络功能已测，也不把测试瞬时剩余当成可以永久分配的额度。原48 KiB内核堆不是全部内部动态内存；SRAM尾部总长约219–221 KiB还要扣除内核堆预留，不能把它当独立libc池。本轮改为96 KiB内核堆，目标为两个APP传输连接，最终仍以新实测为准。

### 15.1 已有证据与正确解读

- 两款板均报告8 MiB外部RAM，默认内部动态堆49152 B。当前生成配置均未开启TCP、HTTP Client、MQTT库和TLS socket；存在基础Mbed TLS/加密配置不等于TLS握手已经启用或无需额外内存。
- LCKFB G9压力轮次的内部动态堆峰值35660 B，距49152 B上限尚余13492 B，约13.2 KiB；恢复2048后使用16184 B、余32740 B，约32.0 KiB。
- 微雪G9压力轮次峰值41764 B，距上限尚余7388 B，约7.2 KiB；恢复Gfx Show后使用32532 B、余16396 B，约16.0 KiB。微雪双8 KiB内部预拷贝是现有显示负担，不能拿它当网络的空闲空间。
- 两轮PSRAM探针均曾成功分配5 MiB连续块，并同时放入8个150 KiB块。这只证明当时至少能满足这些申请，不是精确剩余量，更不是网络服务或每个APP可独占的保证。
- shell输出的PSRAM `used=8003936 ... 95%`是静态区加配置堆区域的链接布局统计，不是运行时已用掉95%的堆。WAMR上限、外部共享堆和APP内存不能相加当作互不重叠的空间。
- 内部48 KiB动态堆不是芯片全部SRAM。新增静态线程栈、网络池与IRAM代码还会改变链接占用，必须同时检查ELF与运行时，不能只凭动态堆余额判定整机能否承载。

历史数据来源：`docs/validation/graphics-g9-2026-10-14.md`及仓库外G9两板cleanup/stress记录。两板场景和分辨率不同，数字用于各自预算，不作跨板协议吞吐比较。

### 15.2 建议实际加入的最小集合

1. **保留并整合Wi-Fi状态、DNS、SNTP**：已有能力优先复用，不增加重复服务线程，也不默认启用热点和station双网络并发。
2. **异步TCP客户端及有界UDP端点**：纳入两个APP传输名额，按需使用。UDP用在局域网小报文，不默认常驻发现监听。
3. **一个HTTP/HTTPS客户端请求**：流式下载，2 KiB级响应缓存，禁止整包入内存。下载总量可以大于缓存，但受APP磁盘、总字节和总时长限额约束。
4. **一个MQTT/MQTTS客户端**：3.1.1、QoS 0/1、4个订阅、1 KiB消息、有界队列。它占用两个APP连接名额中的一个；需验收MQTT＋HTTP、MQTTS＋HTTP及MQTT＋HTTPS，双TLS另行评估。
5. **系统网络统计**：只记录状态和计数，不默认抓包、缓存全量日志或保存请求体。

这里的“共用名额”是资源准入：HTTP/MQTT内部socket也计入总数；两个名额用完后明确返回忙，不能擅自断开长连接或在不可见队列中无限等候。系统DNS/SNTP/DHCP和发现服务另留系统预算。原NET_MAX_CONTEXTS=4不足以直接承诺该并发；N1已验证8个上下文/8个连接处理项及两APP传输名额，采用256字节RX24/TX32分片；原生池高水位与取址恢复见协议池记录。后续HTTP/TLS/MQTT还需按各阶段重新评估，不能沿用本轮结果承诺TLS并发。

### 15.3 TLS是单独的资源门槛

先验证一个HTTPS或一个MQTTS会话，再考虑二者并发。CA、握手、证书解析、加解密缓冲和线程栈均有开销，不能因为PSRAM有空闲就假设96 KiB内核堆和缩小后的libc池就一定能够容纳。

实施要求：

- 按用途区分内部RAM必需区与可放PSRAM区，评估本地TLS分配器/专用有界内存池，禁止仅靠放大默认系统堆解决。
- 共用证书管理和TLS基础设施，HTTP/MQTT不各自复制一套长期证书/池；选定CA资源集合，证书链长度及单证书大小有上限。
- 不任意缩小TLS记录缓冲来换数字：需要验证对端协商、完整证书链和实际TLS记录，否则小响应成功不代表可访问目标服务。
- 测量冷握手、重连和异常退出峰值，同时运行最重的已支持图形/面板路径；无空间时在接纳任务阶段明确失败，不允许中途拖垮UI。
- 作为项目验收目标，新增网络后的压力场景动态堆至少保留8 KiB余量，且栈、共享池和分配失败均通过检查。这个8 KiB是工程目标，不是已达到的事实；微雪旧48 KiB配置在历史峰值后仅余7.2 KiB，本轮改96 KiB后需重新记录峰值；不能把扩大容量全部算成TLS可用预算。
- 若受控实验不能满足内存与响应目标，先交付明确标识的低资源或局域网明文开发配置；面向需要HTTPS/MQTTS的业务必须待TLS配置通过，不以关闭证书验证代替。

不预填“TLS一定占多少KiB”的固定数字；成本随所选算法、证书链、记录配置、分配器和Zephyr版本变化，N2/N3必须给出本项目测量值。

### 15.4 后续哪些值得增加

- **优先选一个WebSocket或SSE**：只有APP需要实时网页/服务器推送时加入，复用TCP/TLS与传输名额；已有MQTT业务不重复开启另一条推送通道。SSE是HTTP流的解析层，不额外建立无关连接。
- **mDNS/DNS-SD按需开关**：只在需要手机自动发现设备时启用；补测组播队列和常驻开销，不能称其完全不耗资源。
- **本地HTTP配网服务限时运行**：只在用户进入配网时启动，退出即关闭，单客户端、有限请求体，不作为常驻Web管理后台。执行模式应与其他APP连接做明确协调。
- **下载进度与校验可优先实现**：尽量用已有HTTP流和文件沙箱组合；首版只做前台任务，后台下载和多任务管理不默认加入。

### 15.5 当前建议不加入默认固件

CoAP/DTLS、LwM2M、MQTT 5/QoS 2、MQTT broker、HTTP/2/3、QUIC、NAT、VPN、通用文件服务器、多客户端Web服务、无限离线消息、全局常驻后台网络任务及双TLS并发，都先不纳入默认镜像。不是确认硬件绝对不能运行，而是目前缺少足以抵偿资源与维护成本的APP需求及实测预算。

固件OTA继续独立评估分区/启动链和断电恢复，不作为“顺手加一个网络协议”的项目。IPv6及复杂企业网络根据实际部署决定，不默认改变两板配置。

### 15.6 按资源门槛推进

N1先测单连接再测两个TCP/UDP连接；N2评估HTTP/HTTPS请求；N3复用相同服务/池支持MQTT/MQTTS，并测试MQTT与HTTP共存；N4在两板重负载下验收；N5按子项加入WebSocket、发现、本地服务与下载增强。双TLS仍为单独的资源门槛。网络优化不得回退现有显示稳定性、字体质量、触摸和上下拉恢复。


## 16. 内核堆96 KiB与libc堆统计（本轮已修改）

### 16.1 修正SRAM尾部计算

本项目已有`patches/aster_zephyr_v4.4.2_sram_tail_heap.patch`。底层`kernel/mempool.c`的`z_sys_heap_sram_tail_reserve()`从对齐后的`_end`到`_heap_sentry`之间预留内核堆；libc `malloc_prepare()`再扣除同一预留。改变堆大小不一定移动ELF的`_end`，因为内核堆是在启动时分池，并非普通BSS数组。

正确关系：SRAM尾部总长度＝内核堆预留＋libc arena，另扣对齐与各堆管理元数据。前一轮把尾部总长直接称为libc容量，多算了48 KiB；该旧估算已纠正，不再作为预算依据。

扩容前读取的ELF基线：

- 微雪：`_end=0x3fcb2468`，`_heap_sentry=0x3fce9704`，对齐后的尾部总长225944 B，约220.65 KiB；扣48 KiB后libc arena约172.65 KiB。
- LCKFB：`_end=0x3fcb2ab8`，同一sentry，尾部总长224328 B，约219.07 KiB；扣48 KiB后libc arena约171.07 KiB。

静态对象不变时，96 KiB内核堆对应libc arena约123–125 KiB；128 KiB则约91–93 KiB。本轮新增统计/日志可能略改静态占用，必须以新构建和实机报告为准，不能把估算当空闲量。

### 16.2 配置与监测

本轮修改两板`base.conf`与微雪`qspi-prefetch.conf`，内核堆设为98304 B。微雪继续双8 KiB预拷贝、40 MHz、RGB565，不启用双16 KiB实验方案。双16 KiB/80 KiB历史实验配置保留独立用途。

`aster sys mem`新增libc堆`usable/peak/used/free`，来自`malloc_runtime_stats_get()`；`usable`为已用＋空闲的可分配统计，不含堆元数据，也不是仅凭ELF地址相减。原`dram heap`继续报告内核堆，明确其与libc worker stack的区别，保持现有命令入口和主要输出格式。

libc主要消费者为`aster_dram_alloc()`分配的APP执行、Wi-Fi任务、音频、文件服务、显示/绘制、时间同步和看门狗线程栈，以及libc小对象。栈按配置名义合计约46 KiB，另有条件线程、对齐及其他库分配；不能把名义合计当作运行时峰值。

### 16.3 本轮验证与完成条件

- 两款板均需确认生成配置实际为98304 B，未被其他片段覆盖。
- 两款板均需编译成功，保持板型、显示配置及APP ABI不变。
- 已接入板读取两套堆，循环启动已有APP，创建Wi-Fi工作线程并检查上下拉；记录稳态及峰值，保持APP集合/音量/用户文件。
- 未接入板只记构建通过，不写成实机通过。
- 新内核堆峰值有余量且libc栈申请无失败；后续网络协议引入后重复N1–N4，并测试实际TLS分配器使用的池。
- 96 KiB足够时不继续扩128 KiB；扩容是两套堆的重新分配，不是增加物理SRAM，也不改变8 MiB PSRAM容量。

本轮尚不实现HTTP/TCP/MQTT等协议；新内存布局只是其前置条件。

本轮两板构建和固件97项测试通过。LCKFB刷入96 KiB版，2048/Snake/IMU各两轮共6次启动、RUNNING及退出、Wi-Fi扫描和两轮调音台上下拉注入检查通过。9份内存样本中，内核堆累计峰值35660 B，采样最小空闲65500 B；libc累计峰值67284 B，采样最小空闲61584 B。累计峰值可能发生在采样之间，不能将采样最小空闲等同全过程最小空闲。最终主页内核堆使用15352 B、空闲82720 B；libc可分配统计125768 B、使用64184 B、空闲61584 B。首次按需服务初始化后，两轮APP相应采样保持相同libc使用量，未见逐轮增长；这不替代长期泄漏测试。

测试结束恢复主页、音量38，原17个APP数量保持，未安装/卸载应用；网络连接配置未修改。截图确认主页，无新增人工实体反馈。微雪仅构建，尚未刷入或实机补测；未执行网络协议、TLS或长时压力测试。精简结果见[96 KiB内核堆验收记录](validation/kernel-heap96-2026-10-14.md)。
