# APP 安装、升级与启动恢复

当前实现采用两个程序版本槽及独立提交记录。公开 APP ABI、ASTP 包格式和 SDK CPU 目标保持不变；APP 继续使用 `/assets`、`/data`、`/cache` 等虚拟路径。

## 设备目录

```text
/SD:/aster/apps/<id>/
  .active0                 槽 0 提交记录（24 字节）
  .active1                 槽 1 提交记录（24 字节）
  .v0/                     程序版本槽 0
    package.ast
    app.wasm
    app.aot
    manifest.json
    icon.bin               可选
    assets/                可选
    .installing            仅在该槽尚未完成时存在
  .v1/                     同样布局的程序版本槽 1
  data/                    稳定的用户存档目录
  cache/                   稳定的用户缓存目录
```

旧固件的平铺 `package.ast`、`app.wasm`、`app.aot`、`manifest.json`、`icon.bin` 和 `assets/` 可继续从 APP 根目录读取。首次升级写入新槽，不移动或删除旧布局及其用户数据。平铺文件保留至卸载，以提供兼容回退；随后升级循环复用两个槽，不创建无限增长的版本目录。

SD 必须容纳当前版本和一个完整的新版本，包含原包及展开后的程序/资源。迁移旧布局时还保留平铺版本，因此最多保留两个槽加一个平铺兼容版本。空间不足会报告失败，不能通过预先删除当前版本来腾空间。

## 安装顺序

1. 读取并检查源包、ABI、CPU/AOT、签名策略与 APP ID。非法路径形式的 ID 被拒绝。
2. 在程序文件锁内确认没有正在运行、暂停或启动中的 APP。先返回主页，再部署；忙时返回 `ASTER_EBUSY`。此规则避免修改运行时借用的注册表记录。
3. 校验两份提交记录与各槽，选择非当前槽。读取状态不确定时拒绝修改，避免把当前槽误当成备用槽。
4. 先删除备用槽的旧提交记录，再清理该槽并创建 `.installing`。当前槽及其提交记录保持不变。
5. 将原包、WASM、AOT、有效图标、资源和规范化 manifest 写入备用槽。每个文件都检查打开、完整写入、`fs_sync`、关闭，以及逐字节读回结果。读回不一致也失败。
6. 确保 APP 根目录的 `data/` 存在，保留已有存档和 `cache/`。完成后移除备用槽的 `.installing`。
7. 计算 manifest CRC，生成并写入该槽自己的提交记录；对记录也执行同步、关闭和读回检查。
8. 在同一锁范围内刷新注册表。启动请求只能在刷新完成后取得记录，程序、权限、内存配置与资源路径来自同一代版本。

启动的文件锁在 RUNNING 预留状态发布后、Guest 初始化前释放，避免 APP 的初始化回调调用 appmgr 时发生互相等待。安装、卸载、扫描和桌面图标读取共享该文件锁；锁顺序为 runtime `app_lock` → `files_lock` → registry `reg_lock`。

## 提交与恢复规则

提交记录由 `ASTV` 魔数、格式版本 1、u32 序号、槽号、manifest CRC32 和记录 CRC32 组成，整数使用小端字节序。CRC 用于检查完整性；源包签名仍由原来的安装签名策略验证。

启动扫描检查记录长度、魔数、版本、槽号、记录 CRC、manifest CRC、未完成标记及必需程序文件，并检查 AOT 魔数。在完整候选中按可回绕的序号选择最新槽。未提交、未完成、短写或损坏的记录/槽不参与选择；仍完整的旧槽可被选择。没有可用槽时尝试完整的旧平铺布局。没有可用版本则不将该目录注册为 APP。

恢复不依赖将单次 FAT 重命名当作断电事务，也不在恢复阶段覆盖或搬移用户数据。尚未完成的备用槽可留在卡上，在下一次安全重试中清理。主机故障测试覆盖文件操作完成后的进程中断；FAT/SD 在突然失电时的真实落盘顺序仍需真机验收。

写入提交记录的同步/关闭/读回失败时，安装会报告错误，但记录可能实际上已完整落盘。这种情况下可以选择完整的新版本，也可能继续使用旧版本。注册表在安装失败后也重新扫描以保持一致；安全重试不会删除存档。不要将收到安装失败等同于“设备版本一定没有变化”。

注册表缓存已选择的槽，运行时、图标和 APP `/assets` 使用该槽，避免反复读取提交记录或因瞬时 I/O 错误在运行中切换资源版本。`/data`、`/cache` 始终映射到 APP 根目录。

## 无硬件回归与后续真机验收

`tests/test_install_io.py` 编译并执行真实 C 安装函数、版本选择函数、虚拟路径映射和 manifest 读取函数；文件系统与包解析输入由主机测试适配器提供。用例包括每个 I/O 错误和进程中断前缀、失败重试、损坏记录、资源读回损坏、旧布局迁移、存档保留、缓存槽一致性、序号回绕和运行中 APP 的忙门禁。注册表安装入口另有锁与失败后刷新测试。

manifest 序列化临时缓冲按需放在 PSRAM，避免与嵌套文件系统/CRC 调用挤占 shell 栈；分配失败也返回错误并保留当前版本。

这些测试检查文件集合与恢复状态，不在主机上执行 Xtensa AOT，也不证明 SD/FAT 断电安全。微雪已完成部分故障注入、AOT 和两处真实断电验证；真实满盘、自然介质故障、更多掉电时刻和长期基线仍待验收。具体已测条件和剩余清单见长期验收记录。

硬件验收状态、剩余待测项与仓库内证据统一维护在 [P0 可靠性验收记录](reliability-validation.md)。
